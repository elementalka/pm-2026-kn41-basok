# Контракт навчального каталогу S-11

Версія 1, 16.11.2026. Вхід для планування реального спринта, а не свідчення приймання. Результат — локальний каталог ресурсів зі збереженням стану та перевіркою ролі на сервері. Зовнішні розклад і IdP у цьому ізольованому компоненті не використовуються. S-01/S-09 залишаються окремими історіями; виробничий запуск без них та допуску ІБ заборонений.

## Користувацький сценарій

1. Навчальний адміністратор додає аудиторію `A-103` і обладнання `P-002` із доступністю; обидва коди з’являються в каталозі після повторного відкриття.
2. Навчальний заявник читає каталог, але POST/PUT із його identity отримує HTTP 403 і не змінює даних.
3. Адміністратор архівує `A-103`; заявник більше не бачить її в каталозі для нового вибору. Історичний запис, який посилається на код, зберігає той самий код.

Це три перевірки трьох чинних AC S-11. Пошук вільного інтервалу, подання/погодження заявки й академічна автентифікація до цього компонента не входять. Вільний каталог не означає вільний часовий інтервал.

## Зафіксовані відповіді перед плануванням

| Питання | Відповідь моделі та доказ |
| --- | --- |
| Q-11-01, що означає унікальний код? | Пробіли по краях прибираються, латинські літери приводяться до верхнього регістру; `a-103` і `A-103` — один код. Повторний код повертає HTTP 409. Це прийняте припущення навчальної моделі, не вимір реального каталогу |
| Q-11-02, що робить архівація? | Логічний прапорець; фізичного видалення ресурсів і переписування історичних кодів немає. Архів не потрапляє у видачу заявника |
| Q-11-03, як перевіряти роль без IdP? | Локальний fixture-адаптер Bearer identity з fixtures.json. Перевіряється серверна заборона операції; справжня академічна автентифікація цим не доводиться |
| Q-11-04, хто перевірить результат? | Власник SC-01 — ST-01; у навчальному огляді цю роль явно відокремити від виконавця. Приймання ще не відбулося |

Нових відкритих питань у цьому обмеженому сценарії на 16.11 не зареєстровано. Якщо змінюється хоч одна з відповідей, перед реалізацією змінити цей контракт і повторити DoR; нез’ясоване питання позначити відкритим у таблиці готовності.

## Контракт API для перевірки

GET `/api/resources`: активний каталог для requester; адміністратор може явно запросити архів. POST `/api/resources`: тільки admin, обов’язкові code/name/kind/status, унікальний код, HTTP 201 або 409. PUT `/api/resources/<code>`: тільки admin, зміна name/status/archived зі збереженням коду. GET `/api/history`: лише синтетичні історичні посилання. Невідомий identity — HTTP 401; requester при записі — HTTP 403; неправильні поля — HTTP 400.

Дозволені kind: room/equipment; status: available/unavailable. Локальний сервер слухає тільки 127.0.0.1. Відкриті demo-токени є іменами fixture-персонажів, не секретами виробничої системи.
