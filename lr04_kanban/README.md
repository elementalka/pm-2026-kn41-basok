## 1. Definition of Workflow

| Колонка | Картка потрапляє сюди, коли | Картка виходить звідси, коли |
| --- | --- | --- |
| Backlog | Є ключ, результат та відомі залежності, але вхід або критерії ще не готові | Результат обмежений 1–2 днями, критерій перевірюваний, усі входи доступні; чекліст пройдено |
| Ready | Чекліст готовності пройдено, залежності закриті | Виконавець фактично починає роботу та має вільний слот In progress; фіксується перший start |
| In progress | Почалося редагування/аналіз результату; дата старту записана | Результат існує й доступний для читання, є посилання та вільний слот Review |
| Review | Результат перевіряється за критерієм issue та схемою, якщо вона є | Усі критерії виконані й доказ опублікований — Done; інакше повернення In progress із причиною та вільним слотом |
| Done | Результат закомічений і доступний у main, перевірка успішна; issue закривається | Повторне відкриття лише через конкретний дефект; попереднє завершення позначається скасованим |

Review для одного виконавця — окремий прохід самоперевірки, не вигадане незалежне погодження. На картці `standard` за замовчуванням; `expedite` позначаємо явно в її описі та заголовку.

Створення беремо з `createdAt` issue, завершення — `closedAt` після Done. Перший старт і переходи фіксуємо в журналі нижче та історії Projects у момент події. Дати — Europe/Kyiv, календарні дні. Для кожного наступного переходу додаємо час із часовим поясом, попередню/нову колонку й посилання на доказ. Точний час початкових переходів не використовується: локальний годинник розходився із сервером; дата однакова, послідовність збережена. Надалі джерело часу — сервер GitHub.

Блокер фіксується на issue: причина, початок, закінчення, рішення. Картка залишається в активній колонці та рахується у WIP. Дні в блоці — сумарна тривалість неперекривних інтервалів у календарних днях (частки дня дозволені). Очікування перед стартом у Backlog не є blocked_days. Для пошуку вузького місця рахуємо всі входи/виходи колонок, включно з поверненнями; один cycle time не доводить, де саме чекали.

Ліміти видимі в назвах колонок і назві Kanban-подання. Контроль ручний: GitHub технічно не забороняє зайве переміщення. Перед кожним pull рахуємо картки, включно із заблокованими. За вичерпаного ліміту нове не починаємо: перевіряємо або завершуємо вже взяте, усуваємо блокер. Expedite не скасовує ліміт; призупинення картки в In progress теж не звільняє слот.

**Коли ліміт спрацював:** поки не зафіксовано. Не зараховуємо наявність числа в назві за доказ роботи ліміту.

## 4. Конверт 1, зменшення ліміту

**Ще не застосовано.** Третій день — 2026-10-15. Текст конвертів прочитано під час підготовки раніше тригерів; це відхилення від порядку ознайомлення в умові, а не проведений експеримент. Стан «до» ще не зафіксовано: він має відповідати саме моменту зміни.

На тригері записати кількість і ключі активних карток, потім змінити ліміт In progress 3 → 2 і назву колонки; спостерігати щонайменше два дні. Якщо ліміт не стримав роботу — зменшити до реально обмежувального значення та спостерігати ще два дні. Записати конкретну картку, яку не почали, що завершували натомість, та фактичні завершення до/після. Висновок про швидкість зараз відсутній.

## 5. Конверт 2, термінова картка

**Ще не застосовано:** п’ята картка не завершена. Перед застосуванням зберегти стан колонок. Створити F-013 класу expedite для навчального термінового запиту перевірки/виправлення `lr01_case`. Умова про «два дні до дедлайну» — сценарій конверта, не фактичний календар курсу.

Ліміт не скасовувати: спочатку завершити/вивести із зайнятого слоту поточну роботу за правилами потоку. Якщо свідомо повертаємо незавершене в Ready, записати витіснення, зберегти перший start та включити очікування в cycle time. Зафіксувати витіснену картку, час появи й завершення expedite, результат валідатора. Якщо реальних помилок немає — записати це, не псувати файли заради сценарію.

Попередня відповідь про три expedite на тиждень: вони витіснятимуть standard і збільшуватимуть час очікування. Одна термінова картка одночасно в межах спільного WIP; кожен додатковий запит потребує явного рішення про пріоритет. Окрема позначка/смуга поліпшує видимість, але не створює ємність. Остаточний висновок — після події.

## 6. Перший вимір

Фінальний вимір ще не проводився. Формула для завершеної картки: `cycle_time = done_date − start_date`, у календарних днях Europe/Kyiv; того самого дня — 0. Середнє: сума cycle time / число завершених карток. Незавершені картки у знаменник не входять.

| Показник | Значення |
| --- | :-: |
| Найкоротший cycle time, днів | —, вимір попереду |
| Найдовший cycle time, днів | —, вимір попереду |
| Середній cycle time, днів | —, вимір попереду |
| Завершених карток у фінальному вимірі | —, вибірку ще не закрито |

Колонку найдовшого очікування поки не визначено. Її визначимо за журналом переходів, окремо від загальної тривалості карток. Менше восьми завершених зараз, бо це запуск дошки, а не кінець спостереження. Планова ціль — 12, мінімум за умовою — 8; виняток 4–7 потребує пояснення фактичної причини після двох тижнів.

Під час наступного планування треба перевірити остаточний беклог ЛР06 повторно, включно з новими історіями.
